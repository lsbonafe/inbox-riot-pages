# Issue format

Each published issue is a JSON file in `src/data/issues/` named `YYYY-MM-DD.json`. Store only edited public content. The private instance sets the site language; write all editorial text in that language. The original article remains available through its source link.

Required fields: `title`, `date`, `edition`, `dek`, `editorNote`, `leadTopics`, and `stories`. A new issue uses `schemaVersion: 2`, a named `artPalette`, and an original `cover` with `kind`, local `src`, `alt`, `credit`, and `rights`. A revision sets `revisedAt` without changing its original date, edition, or URL; it may retain story IDs and sources from that same issue while checking for duplicates in other issues. Display capitalization belongs in CSS, so use normal sentence case in JSON.

Each lead topic is a ranked theme with a stable `id`, `title`, central `claim`, substantial `takeaway`, `whyItMatters`, `uncertainty`, original article-specific `image`, and one or more supporting `storyIds`. The takeaway synthesizes the supporting work in two to four sentences. Use fewer leads for a small issue and reserve the lead position for the strongest theme.

Each story needs a stable public `id`, `section`, `headline`, `sourceName`, `takeaways`, and `whyItMatters`. Set `treatment` to `feature` for deeper coverage or `brief` for a compact, sourced takeaway. Every Read also records the source's BCP 47 `sourceLanguage`, such as `en` or `pt-BR`; this metadata does not change the language of the zine's editorial text or create a visible badge. Translate non-native sources faithfully. For an excerpt, use a brief attributed translation or omit it. Reads may use `beat` to group a large issue: `engineering`, `economics`, `accountability`, `frontier`, or `culture`.

Use `sourceUrl` for a canonical public article or `emailReference` for an email-only publication; never put a mailbox message ID or private mailbox URL in either. Optional `relatedLinks` holds labeled canonical public URLs for underlying studies. Keep the original article as `sourceUrl` whenever one exists. An `image` needs `kind`, `src`, `alt`, `credit`, and `rights`. `kind: original` uses a local `assets/` path; `kind: source` uses a direct public HTTPS image URL. For new issues, article illustrations are original and specific to the article; source images are reserved for releases where they are appropriate and credited. For SVGs generated by `npm run art:render`, add a supported `motif`, short `label`, and `artStyle` with a `template` and `palette` named in `DESIGN_SYSTEM.json`.

`fieldNotes` are optional personal dispatches when the owner has authorized them in the private prompt. Each note has a stable `id`, `title`, specific `event`, worthwhile `angle`, and a human-readable email `sourceReference`. Choose the strongest note as the visual star. At most one note per issue may have a local original `sticker` image with alt text, credit, and rights; other notes stay unstickered. Draw the cutout for that event and place it on its note card, never as a generic section badge. Optional `contextLinks` cite independent public sources for external claims. The angle may be practical, cultural, economic, funny, skeptical, or personal; choose what the event supports. Remove buyer identities, addresses, prices paid or received, and private identifiers. Do not infer motive from a transaction.

Sections: `reads`, `signals`, `releases`, `offers`, `noise`. Use `reads` for articles, essays, and substantial videos where the point is what the source found or argued. Use `signals` for specific changes or announcements. Lead topics reference stories without repeating their full text.

Keep a large inaugural issue navigable with an index, clear headings, full cards for the strongest stories, and compact briefs for the rest. Version 2 requires original art for its cover and every lead; it does not require filler images in Reading Room or Signal Desk. Every New Releases item needs a relevant image. Choose each image for the particular subject and avoid reused compositions or repeated image files.
